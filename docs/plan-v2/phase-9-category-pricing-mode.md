# المرحلة 9 — وضع التسعير على مستوى الفئة (Category Pricing Mode)

> نتجت من نقاش مع مازن بعد Phase 3/4 (الأسعار + الطلب المتعدد): كتالوج
> الأسعار (`Offering`) لازم يكون **اختياري لكل فئة**، الأدمن هو اللي يقرر
> أي فئة تستخدمه (شقق مفروشة، أبواب مصفحة) وأيها تفضل بالنموذج البسيط
> (مقاولات عامة، تشطيب — أسعارها بتختلف كل مرة). وبعد نقاش تاني، اتفقنا
> إن رحلة العميل نفسها لازم تتوحّد لمسار واحد واضح، مش تتسيب زي ما هي.

| | |
|---|---|
| **الاعتمادية** | فوق Phase 3 (Offerings) — لازم يكون خلص |
| **migration** | ✅ واحدة — عمود `pricingMode` على `Category` |
| **ship** | جزء باك إند + أدمن أولًا، بعده جزء الفرونت (العميل + البروفيدر) |

---

## 1. القرار الجوهري

```prisma
enum CategoryPricingMode { QUOTE_ONLY FIXED_CATALOG }
```

على `model Category`: `pricingMode CategoryPricingMode @default(QUOTE_ONLY)`.

- **`QUOTE_ONLY`** (الافتراضي لكل الفئات الموجودة — صفر تأثير رجعي): مفيش
  كتالوج أسعار. الشركة تعرض خدماتها كـ chips عادية (زي دلوقتي)، والعميل
  بيدوس "اطلب الخدمة" ويوصف طلبه، والسعر بيتحدد بالاتفاق المباشر.
- **`FIXED_CATALOG`**: الشركات في الفئة دي تقدر تعمل `Offering` بسعر واضح،
  والعميل بيشوف كروت أسعار حقيقية ويقدر يختار أكتر من خدمة مع بعض.

**ليه enum مش boolean:** لو احتجنا وضع تالت بعدين (مثلًا "كتالوج اختياري —
البروفيدر يقرر" أو "هجين") بنضيف قيمة جديدة للـ enum من غير ما نغيّر شكل
البيانات القديمة. Boolean كان هيحتاج migration جديدة تمامًا لو الاحتياج ده جه.

### ليه التأثير الرجعي صفر
`OfferingCards.tsx` (الفرونت) أصلًا فيه fallback جاهز: لو الشركة مالهاش
Offerings تظهر الـ chips القديمة تلقائيًا. يعني تفعيل/تعطيل الوضع الجديد
**مابيلمسش** أي Offering موجود بالفعل — بيتحكم بس في **قدرة البروفيدر إنه
يضيف/يعدّل من دلوقتي** وفي **شكل أزرار الطلب عند العميل**. مفيش داتا قديمة
بتختفي.

## 2. الباك إند

### السكيما
```prisma
enum CategoryPricingMode { QUOTE_ONLY FIXED_CATALOG }

model Category {
  // ...الحقول الموجودة
  pricingMode CategoryPricingMode @default(QUOTE_ONLY)
}
```
migration واحدة، إضافية بس (عمود جديد بـ default) — راجع قاعدة الـ
migrations الإضافية في `docs/plan-v2/README.md`.

### الحماية الفعلية — مش بس إخفاء تبويب
في `api/src/lib/services/offerings.service.ts`، أي عملية إنشاء/تعديل/نشر
لـ `Offering` أو `BundleRule` أو `OfferingTier` لازم تتأكد إن
`company.category.pricingMode === "FIXED_CATALOG"` قبل ما تنفّذ، وترمي
`ValidationError` (أو `403`) لو لأ. **من غير الشرط ده، إخفاء التبويب في
الواجهة مجرد ديكور** — أي حد يقدر يبعت الطلب مباشرة للـ API ويعدّي.

### العقد (apiTypes)
ضيف في الاتنين (`api/src/lib/apiTypes.ts` و `app/src/lib/apiTypes.ts`):
```ts
export type ApiCategoryPricingMode = "QUOTE_ONLY" | "FIXED_CATALOG";

// في ApiCategory
pricingMode: ApiCategoryPricingMode;

// في ApiCompany — مش هنعمل نداء إضافي عشان نعرف وضع فئة الشركة
categoryPricingMode: ApiCategoryPricingMode;
```
`categoryPricingMode` بتتحسب سيرفر-سايد وتترجع مع كل `ApiCompany` (في
`companies.service.ts` — `serializeCompany`)، عشان الفرونت (بروفايل الشركة
وداشبورد البروفيدر) يقرر يعرض إيه من غير طلب إضافي.

### الأدمن — الـ endpoint
`PATCH /api/admin/categories/:id` (الموجود) يقبل `pricingMode` كحقل زي أي
حقل تاني — مفيش endpoint جديد، الفاليديشن في
`api/src/lib/validation/categories.ts` بس تتوسع.

## 3. الأدمن — `CategoryEditor.tsx`

سويتش/راديو جديد في نفس الفورم الموجود، تحت وصف الفئة مباشرة:

```
كتالوج الأسعار
○ بسيط — العميل يطلب ويتفق على السعر مباشرة (الافتراضي)
○ كتالوج أسعار ثابت — الشركات تقدر تعرض أسعار واضحة والعميل يختار ويشوف الإجمالي
```

- استعمل نفس نمط الحقول الموجودة في الملف (`LField`, `field-input`).
- تحت الاختيار الثاني، سطر توضيحي صغير (`text-[12px] text-outline`):
  "الشركات في الفئة دي هتقدر تضيف أسعار من داشبورد البروفيدر بعد الموافقة".
- **تحذير عند التبديل من `FIXED_CATALOG` لـ `QUOTE_ONLY`** لو الفئة فيها
  شركات عندها Offerings منشورة فعلًا: "في X شركة عندها أسعار منشورة في
  الفئة دي. تعطيل الوضع مش هيحذفها، بس الشركات مش هتقدر تضيف/تعدّل أسعار
  جديدة." — تأكيد بس، مش منع.

## 4. البروفيدر — إخفاء تبويب الأسعار مش مجرد إخفاء

`ProviderDashboard.tsx:37-48` — `TAB_CONFIG` دلوقتي array ثابتة فيها
`pricing` دايمًا. لازم تتحول لدالة/فلترة:

```ts
const tabs = TAB_CONFIG.filter((tb) =>
  tb.id !== "pricing" || company?.categoryPricingMode === "FIXED_CATALOG"
);
```

- لو البروفيدر كان فاتح تبويب "الأسعار" وبعدين الأدمن عطّل الفئة (حالة
  نادرة بس ممكنة)، والتبويب المختار حاليًا بقى مش موجود في `tabs` — ارجّعه
  لـ `overview` تلقائيًا (`useEffect` بسيط يتأكد إن `tab` لسه موجود في
  `tabs.map(t=>t.id)`).
- لو البروفيدر وصل للتبويب برابط مباشر (deep link) وفئته مش `FIXED_CATALOG`،
  اعرض `EmptyState` برسالة "كتالوج الأسعار مش متاح لفئة نشاطك حاليًا" بدل
  ما يشوف شاشة فاضية أو خطأ.

## 5. العميل — توحيد مسار الطلب (الجزء الأهم)

### المشكلة اللي بنحلها
في `CompanyProfile.tsx` فيه **٤ نسخ منفصلة** من زرار "اطلب الخدمة"،
والأربعة بتوصل لفورم فاضي من غير ما تمر على كروت الأسعار خالص:
1. هيدر الديسكتوب (~سطر 236)
2. هيدر الموبايل (~سطر 141)
3. كارت الـ sidebar في تبويب "نظرة عامة" (~سطر 393-398)
4. أسفل تبويب "المشاريع" (~سطر 445-452)

عميل بيدوس أول زرار يشوفه (غالبًا رقم ١ أو ٢) وميعرفش أصلًا إن فيه كروت
أسعار وسلة تحت — فبيوصف طلبه من غير ما يشوف حاجة.

### الحل — سلوك موحّد للأربعة، بس لما الشركة `FIXED_CATALOG`

استبدل الأربعة بمكوّن واحد مشترك `PricingCTA` (`app/src/components/`)،
يتنادى بنفس مكان كل زرار قديم، وبيتصرف كده:

```ts
if (categoryPricingMode === "FIXED_CATALOG") {
  // النص: "اختر الخدمات" بدل "اطلب الخدمة"
  // الفعل: onClick بدل Link مباشر —
  //   1. لو tab !== "Overview" → setTab("Overview")
  //   2. scrollIntoView({ behavior: "smooth" }) لقسم كروت الأسعار
  //      (id="pricing-section" على الـ <section> اللي فيها OfferingCards)
  //   3. أضف كلاس highlight مؤقت (halo خفيف حوالين القسم، يختفي بعد ~1.2s)
  //      — يتخطى في prefers-reduced-motion (سكروول بلا هالة)
} else {
  // نفس السلوك الحالي بالظبط: <Link to={requestHref}>
}
```

- الحالة البيزي (`busy`) **متتأثرش** — لسه "انضم لقائمة الانتظار" زي ما هي،
  التوحيد ده لحالة "متاح" بس.
- قسم كروت الأسعار في تبويب "نظرة عامة" ياخد `id="pricing-section"` +
  `scroll-margin-top` مناسب (عشان الهيدر الملتصق مايغطيش أول الكروت بعد
  الـ scroll).
- الـ highlight البصري: `ring-2 ring-primary/40 rounded-2xl` بتتضاف
  وتتشال بـ `setTimeout`، أو CSS keyframe قصيرة زي أنماط الـ reveal
  الموجودة في `index.css`.

### الرابط الثانوي — الهروب للطلب المخصص
تحت كروت الأسعار مباشرة (نهاية قسم `OfferingCards`)، رابط نصي خفيف الوزن:

```
طلبك مش من ضمن دول؟ اطلب طلب مخصص →
```

- `text-primary text-[13px] font-bold hover:underline` — نص لا زرار، عشان
  يبقى وزنه البصري أقل بكتير من "اختر الخدمات".
  بيوديك مباشرة لـ `requestHref` (نفس الفورم الفاضي القديم).
- ده الحل لعميل عنده طلب خاص مش موجود في القائمة (مثلًا شقة مفروشة
  بمواصفات غريبة) — الباب يفضل مفتوح، بس مش منافس بصريًا للمسار الأساسي.
- الرابط ده يظهر **بس** لو `categoryPricingMode === "FIXED_CATALOG"`
  ومحل واحد فقط (تحت الكروت) — مش مكرر في الأربع أماكن القديمة.

### الفورم نفسه — صفر تغيير إضافي
`RequestForm.tsx` أصلًا بيقرا من السلة (`readCart`) لو موجودة، وبيرجع
للسيلكت القديم لو مفيش عروض. مفيش حاجة تتغيّر هنا — التوحيد كله في
الـ CTA على صفحة البروفايل.

## 6. تشيك ليست الجودة (نفس معيار Phase 8، إجباري)

      المرحلة دي، مفيش أي فرق يلاحظه حد.
- [ ] جرّب فئة `FIXED_CATALOG` من الأربع أماكن كلهم (هيدر ديسكتوب، هيدر
      موبايل، sidebar، أسفل المشاريع) — الأربعة بيوصلوا لنفس النتيجة.
- [ ] الـ scroll + الـ highlight شغالين في RTL وLTR، وبيحترموا
      `prefers-reduced-motion`.
- [ ] بدّل فئة من `FIXED_CATALOG` لـ `QUOTE_ONLY` وشركة عندها Offerings
      منشورة بالفعل — الـ Offerings **تفضل ظاهرة للعميل** (مفيش حذف رجعي)،
      بس تبويب الأسعار عند البروفيدر يختفي.
  البروفيدر لو كان فاتح تبويب الأسعار وقت التبديل، يترجع لـ overview
      تلقائيًا من غير شاشة بيضا أو خطأ.
- [ ] محاولة إنشاء Offering من API مباشرة لشركة في فئة `QUOTE_ONLY` → ترفض
      (تحقّق فعلي في السيرفر، مش بس تبويب مختفي).
- [ ] كل نص جديد في `i18n.ts` بالعربي والإنجليزي.
